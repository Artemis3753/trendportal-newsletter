## 1. 배경

현재 이 채널이 독자와 만나는 창구는 인스타그램 하나뿐이다. 매주 카드뉴스를 발행하고 있지만, 새로운 독자에게 닿는 경로가 인스타그램 하나로 고정되어 있어 구독자 풀을 넓힐 수단이 없다.

또한 발행한 콘텐츠가 플랫폼 안에만 남기 때문에, 지난 글을 찾아보거나 외부에서 검색으로 유입되는 경로가 없다. 독립된 웹사이트는 이 두 가지를 동시에 해결하는 창구가 된다.

---

## 2. 목표

인스타그램 외의 유입 경로를 만들어 구독자 풀을 넓히고, 웹사이트에 일정 수 이상의 정기 방문자를 확보한다. 확보한 방문자 수를 근거로 브랜드 광고를 유치한다.

### 2.1 성공 기준

게시글당 조회수 1,000 이상을 달성하고, 광고 문의를 기존 대비 10% 늘린다.

| 지표 | 목표치 | 어떻게 측정하는가 |
|---|---|---|
| 게시글당 조회수 | 1,000 이상 | 조회수 집계 (F-09) |
| 광고 문의 건수 | 기존 대비 10% 증가 | 클라이언트가 직접 집계 |
| 이메일 구독자 수 | *미정 (Q-13)* | 스티비 주소록 |

> 위 두 목표치는 **비교 기준과 측정 기간이 아직 정해지지 않았다** (Q-16). "조회수 1,000"이 발행 후 한 달 기준인지 누적인지, "10% 증가"가 무엇 대비인지에 따라 달성 여부가 달라진다.

### 2.2 목표가 아닌 것

- **인스타그램을 대체하는 것.** 인스타그램은 계속 주력 채널로 유지된다. 웹사이트는 창구를 하나 더하는 것이지 옮기는 것이 아니다.
- **웹사이트 자체로 수익을 내는 것.** 사이트에 광고를 붙이거나 유료 콘텐츠를 파는 계획은 없다. 사이트는 광고를 유치하기 위한 자산이지 수익원이 아니다.
- **커뮤니티를 만드는 것.** 독자 간 상호작용(댓글, 회원, 포럼)은 이번 범위가 아니다.

## 3. 사용자

### 3.1 운영자 (클라이언트)

인스타그램 트렌드 매거진을 운영하는 1인 운영자. 노션을 오래 사용해 왔고 익숙하다.

**하는 일**

- 매주 금요일 카드뉴스를 발행한다
- 브랜드 / 트렌드 / 광고 / 인터뷰 네 갈래의 콘텐츠를 다룬다
- 광고주와 직접 소통한다

**무엇이 편해야 계속 쓰는가**

- **새 도구를 배우지 않아도 되어야 한다.** 이미 쓰는 노션에서 글을 쓰면 그것으로 끝나야 한다. 웹사이트용으로 한 번, 이메일용으로 또 한 번 쓰게 되면 오래가지 못한다.
- **발행이 한 동작이어야 한다.** 웹사이트 반영과 이메일 발송이 따로 놀면 둘 중 하나를 빠뜨리게 된다.

**이 사람이 하지 않아야 하는 일**

- 코드를 만지는 일
- 이미지 크기를 맞추거나 HTML을 다루는 일
- 구독자 명단을 직접 관리하는 일

### 3.2 독자

인스타그램에서 이 채널의 카드뉴스를 보는 사람. 대부분 모바일로 접근한다.

**어디서 오는가**

- 인스타그램 프로필의 링크
- 인스타그램 게시물의 "링크는 프로필에" 형태의 안내
- 검색엔진 — 웹사이트를 만든 뒤 새로 생기는 경로

**무엇을 하는가**

- 관심 있는 주제의 글을 찾아 읽는다
- 지난 글을 다시 찾아본다 — 인스타그램에서는 어려운 일이다
- 마음에 들면 이메일 구독을 신청한다

**무엇이 있어야 하는가**

- 모바일에서 읽기 편한 화면
- 지난 글을 찾을 수 있는 수단 (카테고리 필터, 검색)
- 구독까지 가는 짧은 경로

## 4. 범위

### 4.1 포함하는 것

1. 글 목록 페이지 (카드 그리드, 최신순)
2. 글 상세 페이지
3. 카테고리 필터
4. 사이트 내 검색
5. 노션 연동, 노션 이미지 만료에 대한 대응
6. 노션 → 스티비 자동 발송
7. 이메일 구독 폼
8. 조회수 집계 → 노션에 되돌려 쓰기
9. 모바일 반응형 웹
10. SEO 기본 + OG 태그
11. 개인정보처리방침 + 수신동의 문구

### 4.2 포함하지 않는 것

> ★ 이 문서에서 가장 중요한 칸. "빼먹은 것"과 "알면서 뺀 것"은 완전히 다른데, 문서에 없으면 구분할 방법이 없다.

| 항목 | 왜 빼는가 |
|---|---|
| 댓글 / 좋아요 | 운영자가 1인이라 스팸·악플 관리 부담을 감당할 수 없다. 독자 반응은 기존 인스타그램 채널에서 이미 받고 있다 |
| 구독 취소 페이지 | 스티비가 제공하는 것을 사용한다. 법적 요건이 걸린 기능을 직접 만들면 틀렸을 때 책임이 이쪽으로 온다 |
| 운영자용 관리자 페이지 | 노션이 이 역할을 한다. 운영자가 이미 익숙한 도구다 |
| 다크모드 | 색 체계를 두 벌 관리해야 한다. 디자인이 안정된 뒤로 미룬다 |
| 다국어 | 독자가 한국어권이다 |
| 소셜 로그인 / 회원 기능 | 구독은 이메일 주소 하나면 된다. 계정을 만들면 비밀번호 관리 책임이 생긴다 |

### 4.3 조회수 집계 방식에 대한 메모

조회수는 집계하되 **자체 대시보드를 만들지 않는다.** 집계한 값을 노션 데이터베이스의 속성으로 되돌려 쓰고, 운영자는 노션에서 글 목록을 보듯 조회수를 확인한다.

- 대시보드 UI가 필요 없다
- 로그인이 필요 없다 — 노션 접근 권한이 곧 인증이다
- 운영자가 새 도구를 배울 필요가 없다

다만 카운트를 쌓아둘 저장소는 여전히 필요하다 (Q-11). 봇 방문 제외와 중복 집계 방지도 함께 다뤄야 한다 (10장 참고).

## 5. 사용자 시나리오

### 5.1 발행 흐름

운영자가 글을 쓴 뒤 독자에게 닿기까지의 순서.

1. 운영자가 **노션 데이터베이스에 새 페이지를 만든다.** 제목, 카테고리, 본문, 카드뉴스 이미지를 채운다.
2. 작성이 끝나면 **상태 속성을 "발행"으로 바꾼다.** *(트리거 방식은 Q-08에서 확정)*
3. 시스템이 노션에서 해당 글을 가져온다.
4. 시스템이 **이미지를 자체 저장소로 복사하거나 중계 주소로 바꾼다.** 노션 이미지 주소는 만료되기 때문이다.
5. **웹사이트에 글이 반영된다.** 목록 페이지 최상단에 카드가 추가되고 상세 페이지가 생성된다.
6. 시스템이 **스티비 이메일 API로 뉴스레터를 만들고 발송을 요청한다.** 대상은 스티비 주소록의 구독자 전체.
7. 구독자가 이메일을 받는다. 이메일 안의 "웹에서 보기" 링크는 5번에서 만들어진 상세 페이지를 가리킨다.
8. 이후 독자가 그 글을 볼 때마다 조회수가 집계되고, 주기적으로 **노션의 조회수 속성에 반영된다.**

> ✍️ 5번과 6번이 동시에 일어나야 하는지, 6번이 실패하면 5번을 되돌려야 하는지는 아직 정하지 않았습니다. 구현 단계에서 다룰 문제입니다.

### 5.2 독자 흐름

1. 독자가 인스타그램에서 카드뉴스를 보고 **프로필의 링크를 누른다.** (또는 검색으로, 또는 공유받은 링크로 들어온다)
2. **글 목록 페이지**가 열린다. 모바일 화면에 카드가 세로로 쌓여 있다.
3. 관심 있는 카드를 눌러 **상세 페이지**로 들어가 글을 읽는다.
4. 더 보고 싶으면 **카테고리 필터**로 같은 갈래의 글을 훑거나, **검색**으로 특정 주제를 찾는다.
5. 마음에 들면 **구독 폼에 이메일 주소를 입력**하고 수신동의에 체크한다.
6. 입력한 주소가 **스티비 주소록에 추가된다.**
7. 다음 금요일부터 뉴스레터를 받는다.

> ✍️ 구독 폼을 어디에 놓을지(목록 페이지 하단? 상세 페이지 끝? 고정 배너?)는 디자인 단계에서 정합니다.

## 6. 기능 요구사항

> ✍️ 4.1의 순서를 따라 번호를 붙였습니다. 4.1의 5번(노션 연동 + 이미지 만료 대응)은 완료 조건이 다르므로 F-05와 F-06으로 나눴습니다. 우선순위 칸은 제안이며 바꾸셔도 됩니다.

| 번호 | 우선순위 | 기능 | 설명 | 완료 조건 |
|---|---|---|---|---|
| F-01 | 필수 | 글 목록 페이지 | 발행된 글을 최신순 카드 그리드로 보여준다 | 노션에 있는 발행 상태의 글이 모두 최신순으로 나오고, 각 카드에서 상세 페이지로 이동된다 |
| F-02 | 필수 | 글 상세 페이지 | 글 하나의 전체 내용과 카드뉴스 이미지를 보여준다 | 제목·카테고리·발행일·본문·이미지가 모두 나오고, 목록으로 돌아갈 수 있다 |
| F-03 | 필수 | 카테고리 필터 | 카테고리별로 글을 추려 본다 | 노션에서 카테고리를 추가·변경해도 코드 수정 없이 반영된다 |
| F-04 | 필수 | 사이트 내 검색 | 제목·본문에서 키워드로 글을 찾는다 | 정해진 대응 범위(Q-12) 안에서 의도한 글이 검색된다 |
| F-05 | 필수 | 노션 연동 | 노션 데이터베이스에서 글 목록과 내용을 가져온다 | 노션에서 글을 추가·수정하면 사이트에 반영된다. API 키가 브라우저에 노출되지 않는다 |
| F-06 | 필수 | 노션 이미지 만료 대응 | 만료되는 노션 이미지 주소를 대체한다 | 발행 후 충분한 시간이 지나도 이미지가 깨지지 않는다 |
| F-07 | 필수 | 노션 → 스티비 자동 발송 | 발행 시 뉴스레터를 만들어 발송한다 | 운영자가 스티비를 열지 않고도 발송된다. 같은 글이 두 번 발송되지 않는다 |
| F-08 | 필수 | 이메일 구독 폼 | 독자의 이메일 주소를 받아 스티비 주소록에 추가한다 | 주소를 입력하면 스티비 주소록에 나타난다. 잘못된 형식과 중복 입력이 처리된다. 수신동의 체크 없이는 제출되지 않는다 |
| F-09 | 필수 | 조회수 집계 및 노션 반영 | 글별 조회수를 세어 노션 속성에 기록한다 | 노션에서 글별 조회수를 볼 수 있다. 봇 방문과 같은 독자의 반복 방문이 과도하게 반영되지 않는다 |
| F-10 | 필수 | 모바일 반응형 | 모바일 화면에서 읽기 편하게 보인다 | 7.1의 기준 화면 크기에서 가로 스크롤 없이 모든 요소가 보인다 |
| F-11 | 필수 | SEO 메타 태그 및 OG 태그 | 검색엔진과 공유 미리보기에 필요한 정보를 제공한다 | 카카오톡에 링크를 붙였을 때 제목·설명·이미지가 나온다. 검색엔진에 색인된다 |
| F-12 | 필수 | 개인정보처리방침 / 수신동의 문구 | 법적으로 필요한 안내를 게시한다 | 구독 폼에서 처리방침으로 이동할 수 있고, 수신동의가 별도 항목으로 분리되어 있다 |
| F-13 | 선택 | 이메일 "웹에서 보기" 링크 | 뉴스레터에서 상세 페이지로 연결한다 | 발송된 메일의 링크가 해당 글의 상세 페이지를 연다 |

## 7. 비기능 요구사항

### 7.1 모바일 / 반응형

- **모바일 우선으로 설계한다.** 유입의 대부분이 인스타그램이므로 모바일이 기본 화면이고 데스크톱이 확장이다.
- 가로 **360px 화면까지** 가로 스크롤 없이 정상 표시된다.
- 카드뉴스 이미지는 세로로 긴 경우가 많으므로, 화면을 넘지 않도록 비율을 유지하며 축소된다.
- 터치 대상(버튼, 링크)은 손가락으로 누를 수 있는 크기를 확보한다.

### 7.2 SEO 및 공유 미리보기

- 모든 글 상세 페이지가 **검색엔진에 색인될 수 있는 형태**로 제공된다. 자바스크립트를 실행해야만 내용이 보이는 구조를 쓰지 않는다.
- 각 글마다 고유한 제목과 설명 메타 태그를 갖는다.
- **OG 태그**(제목, 설명, 대표 이미지)를 제공한다. 카카오톡·인스타그램·슬랙에 링크를 붙였을 때 미리보기가 뜬다.
- 대표 이미지는 해당 글의 카드뉴스 첫 장을 사용한다.
- `sitemap.xml`과 `robots.txt`를 제공한다.

### 7.3 성능

- 모바일 네트워크에서 **목록 페이지의 첫 화면이 실용적인 시간 안에 뜬다.** 구체적 기준은 배포 후 실측해서 정한다.
- 이미지는 **화면에 들어올 때 불러온다.** 카드뉴스 이미지가 많으므로 한 번에 모두 받으면 느려진다.
- 노션 API를 방문자마다 호출하지 않는다. 미리 만들어 둔 결과를 재사용한다.

> ✍️ 성능은 숫자를 먼저 정하고 맞추기보다, 실제로 배포한 뒤 측정해서 기준을 잡는 편이 낫습니다. ⑧ 단계에서 실측 후 이 칸을 갱신하세요.

### 7.4 법적 요건

> 구체적 요건은 아직 확인 전이며, 로드맵 ⑦ 단계에서 원문을 확인할 예정이다 (Q-07).

- **개인정보처리방침 게시** — 구독자 이메일을 수집하므로
- **수신동의 절차** — 구독 시점에 동의를 받고 그 기록을 남긴다. 동의는 다른 약관과 분리된 별도 항목이어야 한다
- **수신거부 방법 제공** — 스티비 기능을 사용한다
- **광고성 정보 표기** — 광고 콘텐츠가 포함될 경우 제목 표기 의무가 있는지 확인 필요
- **발신 도메인 인증 (SPF / DKIM)** — 법적 요건은 아니지만, 없으면 메일이 스팸함으로 분류된다. 도메인 구매 후 DNS에 설정한다

### 7.5 유지보수

- 운영자가 **코드를 만지지 않고** 콘텐츠를 추가·수정·삭제할 수 있다.
- 카테고리가 바뀌어도 **코드 수정이 필요 없다.**
- API 키와 같은 비밀값은 저장소에 커밋되지 않는다.

## 8. 기술 스택 및 선택 근거

| 프레임워크 | Next.js (App Router) | 노션 API 키를 브라우저에 노출할 수 없고, 만료되는 노션 이미지 주소(F-06)를 중계해야 하므로 **서버가 필요하다.** Next.js는 이 기능이 프레임워크에 내장되어 있다. 또한 재배포 없이 콘텐츠를 갱신하는 방식을 기본 지원해, "노션에 올리면 사이트에 반영된다"는 요구와 맞는다.<br><br>**기각 — Astro**: 콘텐츠 사이트에 특화되어 더 가볍지만, 기본이 빌드 시점 생성이라 글이 올라올 때마다 재빌드를 걸어야 한다. shadcn/ui 설정도 손이 더 간다.<br>**기각 — Vite + React (SPA)**: 검색 노출과 공유 미리보기(7.2)가 필수인데 SPA가 가장 불리하다. |

## 부록 A. 확인된 사실

### A.1 공식 문서 원문으로 확인한 것

- **Vercel Hobby 플랜**은 비상업적 개인 용도로 제한되며, 모든 상업적 이용은 Pro 또는 Enterprise 플랜을 요구한다. 상업적 이용의 정의에 "제품이나 서비스의 판매를 광고하는 것"이 포함된다. 단, 후원(Donation)은 상업적 이용에 해당하지 않는다. — <https://vercel.com/docs/limits/fair-use-guidelines>
- **스티비 스타터(무료)**: 구독자 최대 500명, 발송 횟수 월 2회. — <https://help.stibee.com/pricing/understanding/type>
- **스티비 스탠다드**: 월 8,900원~ (구독자 0~500명 구간 / 연 96,000원, VAT 포함), 발송 횟수 무제한. 유료 플랜의 구독자 수 표기는 상한이 아니라 **가격 구간**이다. — 같은 출처
- **스티비 API**: 이메일 API(생성·수정·발송·통계 조회)와 주소록 API(구독자 추가·수정)를 제공한다. 인증은 AccessToken 헤더를 사용하며 기준 주소는 `https://api.stibee.com/v2` 이다. 단 "자동 이메일 API"는 개별 이메일 발송에 최적화되어 있어 **대량 발송에는 적합하지 않다**고 공식 문서가 명시한다. — <https://developers.stibee.com/>, <https://help.stibee.com/api-webhook/api>
- **21st.dev** 컴포넌트는 React + TypeScript + Tailwind CSS + shadcn/ui 규약을 전제한다. 프레임워크는 "Works with Next.js, Vite, Remix, Astro — anywhere React runs"로 자유롭다. 컴포넌트는 패키지로 설치하는 것이 아니라 코드를 저장소에 복사해 넣는 방식이다. — <https://21st.dev>

- Kit(구 ConvertKit) 무료 플랜 구독자 10,000명 / beehiiv 무료 플랜 2,500명, 양쪽 모두 발송 무제한
- Netlify와 Cloudflare Pages의 무료 플랜이 상업적 이용을 허용하는지 여부
- 스티비 무료 플랜에서 API를 사용할 수 있는지 여부
- 한국 정보통신망법상 광고성 정보 전송 시의 구체적 요건
- 21st.dev의 CLI 설치에 멤버십이 필요한지 여부

## 부록 B. 이 프로젝트에 등장하는 세 종류의 이메일

이름이 비슷해서 혼동하기 쉬우므로 구분해 둔다. **코드로 만드는 것은 3번 하나뿐이며, 그것도 받은편지함이 아니라 입력 폼이다.**

| # | 무엇 | 예시 | 누가 처리 | 우리가 구현? |
|---|---|---|---|---|
| 1 | 받는 주소 (문의용) | `hello@도메인` | Gmail 등으로 전달받아 읽는다 | 없음 — DNS 설정만 |
| 2 | 보내는 주소 (뉴스레터 발신인) | `news@도메인` | 스티비가 발송한다 | 없음 — DNS 인증(SPF/DKIM)만 |
| 3 | 구독자 이메일 (독자가 입력) | 독자들의 주소 | 스티비 주소록에 저장된다 | 구독 폼 (F-08) |

도메인은 건물 주소에, 웹사이트는 정문에, 이메일은 우편함에 해당한다. 같은 주소를 쓰지만 서로 다른 DNS 레코드를 보며, 정문과 우편함을 서로 다른 회사에 맡길 수 있다.

## 부록 C. 노션 데이터베이스 명세

클라이언트에게 전달할 명세다. **여기 적힌 속성 이름이 그대로 코드에 들어가므로, 이름이 바뀌면 코드가 깨진다.**

### C.1 속성 목록

| 속성 이름 | 노션 타입 | 누가 채우나 | 용도 |
|---|---|---|---|
| **제목** | 제목 | 클라이언트 | 목록·상세 페이지의 제목 (F-01, F-02) |
| **카테고리** | 선택 | 클라이언트 | 필터 (F-03). 브랜드 / 트렌드 / 광고 / 인터뷰 |
| **상태** | 선택 | 클라이언트 | `초안` / `발행`. **`발행`으로 바꾸는 것이 발행 트리거** |
| **발행일** | 날짜 | 클라이언트 | 최신순 정렬 |
| **슬러그** | 텍스트 | 클라이언트 | 글의 고유 주소. 영문 소문자·숫자·하이픈만 사용 (예: `2026-fall-brand-trend`) |
| **요약** | 텍스트 | 클라이언트 | 목록 카드의 미리보기 문구 + 공유 미리보기 설명 (F-11) |
| **대표 이미지** | 파일 | 클라이언트 | 목록 카드 썸네일 + 공유 미리보기 이미지 (F-11) |
| **조회수** | 숫자 | **시스템** | F-09. 시스템이 주기적으로 갱신한다 |
| **발송 완료** | 체크박스 | **시스템** | F-07 중복 발송 방지. 시스템이 발송 후 체크한다 |

**본문**은 속성이 아니라 노션 페이지 안의 내용 그대로다. 클라이언트는 평소처럼 작성하면 된다.

### C.2 이미지 처리

카드뉴스 이미지는 **본문 안에 전부 넣고, 그중 대표 한 장을 "대표 이미지" 속성에 따로 지정**한다.

- 본문 이미지 → 상세 페이지에 순서대로 표시
- 대표 이미지 → 목록 카드의 썸네일, 카카오톡 등 공유 미리보기
- 양쪽 모두 노션 이미지 주소 만료 대응(F-06) 대상이다

### C.3 슬러그 규칙

글의 주소는 제목과 분리해 둔다. **제목을 수정해도 이미 공유된 링크가 살아 있어야 하기 때문이다.**

- 형식: 영문 소문자, 숫자, 하이픈만 사용
- **비어 있으면** → 노션 페이지 ID로 대체한다 (사이트가 깨지지 않는 쪽을 우선)
- **이미 사용된 슬러그면** → 발행을 막고 알린다 (조용히 다른 주소를 만들면 어느 글이 어느 주소인지 추적할 수 없게 된다)
- **한글이나 공백이 섞이면** → 발행을 막고 알린다

### C.4 클라이언트에게 전달할 주의사항

- **`조회수`와 `발송 완료`는 시스템이 쓰는 칸이다.** 보기만 하고 직접 수정하지 않는다. 특히 `발송 완료`를 실수로 해제하면 같은 글이 다시 발송된다.
- **`상태`를 `발행`으로 바꾸면 되돌릴 수 없는 일이 일어난다** — 이메일이 구독자에게 나간다. 초안 단계에서는 `초안`으로 두어야 한다.
- **속성 이름을 바꾸면 사이트가 동작하지 않는다.** 이름 변경이 필요하면 먼저 알려주어야 한다.
